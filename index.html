The problem

A courier has to stop at every point once and finish where they started, driving as little as possible. That is the travelling salesman problem. It sounds small until you count the routes: 10 points allow about 181,000 distinct loops, 20 allow about 6 × 1016, and 120 allow roughly 10196.

Nobody checks them all. Exact solvers prune the search cleverly, but when you want a good tour right now you build one with a heuristic and accept that it might be a little longer than the best possible loop.

How the tour grows

The tour starts as the convex hull: the rubber-band loop around the outside of the points. Everything else has to be pulled in. Instead of visiting points in some fixed order, the algorithm lets points and edges negotiate.

  1. Every candidate looks at every edge of the tour and picks the one it would stretch least. A candidate is a single point or an arc: a chain of up to a few nearby points.
  2. Every edge looks at every candidate and picks the one that would stretch it least.
  3. A pair is allowed only when the choices agree. The cheapest allowed pair is adopted: the edge breaks and the candidate is spliced in.
  4. Repeat until every point is in the tour.

There are no crossing tests, no inside-the-polygon tests and no area calculations anywhere. The only geometry is the starting hull. Every decision comes from one cost function, so changing what “cheap” means changes the whole behaviour. Arcs are compared per point, which lets a tidy chain of three points beat a lone point that merely fits.

Second thoughts

After each adoption, points and arcs adopted in earlier steps can be lifted back out and re-adopted into a different edge, in either direction, as long as the real tour gets shorter. A point moves at most once per step and hull points never move. When everything is adopted the same loop keeps running as a polish until nothing improves.

On screen, the edges an arc leaves behind flash purple and the arc itself turns orchid.

Forking the timeline

The greedy run always takes the cheapest agreed pair, but several pairs are usually agreed at once. Beam search keeps a handful of partial tours, forks each one into its cheapest few agreed pairs, drops duplicates, and keeps the best. Because one step costs so little, this is affordable: 8 tours with 3 forks each takes about 0.6 seconds at 120 points.

It helps, but less than you might hope. On 8 random 120-point instances with arcs of up to 3 points, the greedy tour averaged 0.86% longer than OR-Tools and the 8-by-3 beam averaged 0.2% shorter. Widening the beam beyond that did not reliably help, and with 8 instances the differences are inside the noise. Running many different configurations and keeping the best did about as well.

How it compares

I ran the construction on 8 random instances at each size and gave OR-Tools the same points: a path-cheapest-arc start, then guided local search for 3 + n/5 seconds, the settings from the original script. Arcs were limited to 4 points.

So the tour lands within about 1% of a strong solver in a fraction of a second, and at 120 points it was shorter than OR-Tools on half the instances. It does not always win: at 30 points OR-Tools matched or beat it every time. This is one run per instance on one machine, not a rigorous study.

The reference inside the visualiser is a different and, in this test, stronger baseline. OR-Tools can't run in a browser, so the page runs a 2-opt and Or-opt iterated search for a second or two instead. It beat OR-Tools on all 8 of the 120-point instances, which is why the gap shown beside the tour is often positive.

Run it yourself

Everything is static files: index.html, a stylesheet and four modules in js/, with no build step. Serve the folder with python3 -m http.server and open localhost:8000. The original Python script, with its matplotlib animation and OR-Tools comparison, lives in tests/ next to the scripts that check the JavaScript port against it and produced the table above.
